Benchmarks¶

The benchmark suite is a fixed set of problems that covers the main code paths. Each case checks its answer against an oracle that does not come from Conatus. A timing is only reported for a run whose accuracy check passed in the same process. Speed figures for Conatus, on this site or in the paper, come from this suite.

python examples/benchmarks/suite.py --threads 1 8            # all cases, default sizes
python examples/benchmarks/suite.py --cases ivp2d_rb --size large --threads 1 2 4 8

The tolerances are written in examples/benchmarks/cases.py from the expected discretisation error, before any run. A case whose error exceeds its tolerance is reported as FAIL and its timing is not used. The eigenvalue cases also require a backward residual below 1e-8.

What is measured¶

  • Wall time of the whole case process, imports included, and its phases: setup_s (model, discretisation, factorisations, the first steps) and run_s (the measured part).

  • Time per step for initial-value cases: the median over blocks of 10 steps, each block one sim.run(steps=10) call, so the per-call cost of run is included as a user pays it. The minimum and the mean over the run are recorded too.

  • Peak resident memory of the case process (ru_maxrss), and the resident memory right after importing Conatus, so that the case’s own share can be read off.

  • Threads: the runner sets OMP_NUM_THREADS, OPENBLAS_NUM_THREADS and MKL_NUM_THREADS to the requested count before the child process starts, and records CN_FFT_WORKERS and CONATUS_BUILD_WORKERS as they are. The BLAS thread pools seen by the process are recorded when threadpoolctl is installed.

  • Hardware and versions: CPU model, host, CPUs allowed to the process, Slurm partition and job; Conatus version and Git commit (with a flag for uncommitted changes), Python, NumPy, SciPy, and the hash of the sources of the compiled core.

Each case runs in a fresh process, one per (case, thread count, repetition). The records are JSON files (kind = "conatus_suite") and a summary table, suite_summary.md.

How to read the numbers¶

A shared node gives noisy times. The suite records the minimum next to the median, and a comparison between two versions is made on the same node type, at the same thread count, with each case’s accuracy check passing in both runs. A speed-up is stated with the two run identifiers.

Threads¶

The implicit solves of a time step are batches of independent banded systems, one per Fourier group. With more than one thread, the compiled core splits a batch over threads, with the Python lock released. Each system is solved by one thread with the same arithmetic as the serial loop, so the state after a step does not depend on the number of threads, bit for bit (tests/core/test_core_threads.py).

The number of solve threads allowed is CONATUS_SOLVE_THREADS if set, else OMP_NUM_THREADS if set, else 1, and never more than the CPUs the process may use. A batch of B systems of n unknowns uses min(allowed, B, √(B n / 900)) threads, and one thread when that is below 2 (fewer than about 3600 unknowns). The rule comes from measurement (run ``, benchmarks/suite/tune_threads.py, one AMD EPYC 9654 node): a batched solve costs about 30 ns per unknown whatever the band width (3 to 12 diagonals each side), and each thread a call starts costs about 27 µs, so that t threads take about T₁/t + 27 µs × t. Measured gains at the chosen count: 1.1 at 4096 unknowns, 2.2 at 16 384, 4 at 65 536; 16 threads were never the fastest on 16 CPUs. explain() of a solver bucket says how many threads a solve uses.

Thread safety. The threaded solve calls OpenBLAS’s LAPACK (gbtrs, getrs) from several threads at once on separate systems; the factors are only read. The only data a solve writes is built on the first transposed solve of each system; since the core builds it for the whole batch with the Python lock held, before any thread starts. Before that change, eight Python threads making the first transposed solve of one batch at the same time corrupted the heap and aborted the process (free(): invalid pointer, with the core). With the change, benchmarks/suite/stress_threads.py found no differing bit in 30 repetitions at 2, 8, 32 and 128 threads, forward and transposed, real and complex (96 systems of 2000 unknowns, 12 diagonals each side), with OpenBLAS on 1 and on 16 threads, nor between eight Python threads solving one batch at once. A ThreadSanitizer build of the core running the same script (2, 8 and 32 threads, eight Python threads) reported no race with the current core and 107 with the core all in the lazy build of the transposed data. ThreadSanitizer sees only the compiled core, not OpenBLAS. In the same run, eight Python threads each stepping its own convection solver at the same time (256 × 64 with 4 solve threads, 16 × 16 × 24 with 8) gave final states equal byte for byte to the same solvers stepped one after the other on one thread.

The grid transforms of the CPU path run on one thread. With f_backend="fused", CN_FFT_WORKERS=N moves its FFTs from numpy.fft to scipy.fft on N threads. The two agree to rounding, not bit for bit, so this stays a choice you make. The default evaluator of the right-hand side does not read this setting.

Cost estimate before a run¶

conatus.cost.estimate predicts the time per step, the run time and the memory of a CPU run before it starts:

import conatus as cn
from conatus.cost import estimate

m = cn.problems.native.rayleigh_benard(Lx=2.0, Ra=1e5, Pr=1)
est = estimate(m, N=(256, 64), scheme="RK443", dt=1e-4, steps=5000)
print(est.explain())

It builds the discretised system, which a run pays for anyway, and takes no step. The prediction is a linear model in features of that system: the band entries touched by one implicit solve, the size of the grid transforms, the number of solves per step and the size of the state. The coefficients were fitted on one thread of an AMD EPYC 9004-series node. They were then checked on resolutions that the fit did not use, and explain() states the largest error found there. estimate(..., calibrate=True) times a banded solve and an FFT for about 40 ms and rescales the coefficients to the machine at hand.

The 0.3.0 times at 8 threads are no better than at one thread: in 0.3.0, more threads only reach the BLAS calls, which a time step barely uses.

The poloidal-toroidal form (decoupled mean flow, potentials φ and ψ) at dt = 5e-3 became non-finite after about ten steps at this resolution in the distributed runs, one rank included. The cause is the initial state, not the distributed path. Its potentials contained sin z and cos(x + z) on a box of length π in z, where they are not periodic. Their slowly decaying Fourier tails gave an initial wall-normal velocity of 1.9, 7.9 and 32.7 at 16, 32 and 64 points per direction, and an advective CFL number of 2.7 at 64 × 49 × 64 and dt = 5e-3. From that state the single-process solver, the distributed solver on one rank and the primitive form all became non-finite after 8 or 9 steps. The distributed solver takes only three-axis domains with one Chebyshev axis and two Fourier axes (RealFourier or ComplexFourier), and only the right-hand side -u·grad(u) plus constant or time-dependent forcing terms (primitive form), or the poloidal-toroidal form. It refuses, with a typed error, every other domain (one or two axes, all-Fourier boxes, two bounded axes, the Legendre, Hermite, Laguerre and compound bases, curvilinear domains), any other right-hand side (for example the temperature advection of a Boussinesq problem), and symmetry subspaces. The grouped transforms take the poloidal-toroidal form on slab grids only.

GPU¶

benchmarks/suite/run_suite_gpu.py runs the four initial-value cases above on the CPU and on one GPU. The problem, resolution, scheme, time step, oracle and tolerance are the case’s own; only the backend changes (backend="cuda", optionally f_backend="fused", or each timed block replayed with sim.solver.run_graph(n)). A GPU time is compared with a CPU time only when both runs pass the case’s oracle check and their errors agree to 5 % of the error. Time per step is the median 10-step block, the GPU synchronised before each block ends; each configuration ran in two interleaved rounds and the table gives the median of the rounds.
